# CS2 引擎数据边界与分析上限

本文把项目字段与 Valve 公开的 CS2 / Source 2 说明对齐。Valve 没有公开完整的 CS2 游戏逻辑源码，因此公开文档用于确认架构事实；更细的字段语义仍需用具体 demo 实测，不能把解析器命名或单个样本当成引擎保证。

## 1. 时间模型：tick 快照与 sub-tick 输入

Valve 说明 CS2 服务器以每秒 64 次的频率发送游戏状态快照，同时以 sub-tick 架构记录移动、射击和投掷等动作发生的时刻。两者并不矛盾：状态快照仍落在 tick 时间格上，动作可以带有 tick 内时间信息。

对分析的影响：

- `tick / 64` 适合作为 tick 级的时间换算；不能据此断言某个 sub-tick 动作准确发生在该 tick 的边界。
- 从 `X/Y` 相邻 tick 差分得到的是该时间段的平均水平速度，不是开火瞬间速度。
- 若 demo 和解析器提供可靠的 sub-tick 输入时间，应将它作为单独时间轴保存；不要把它伪装成更高采样率的位置数据。
- 输入按钮、视角、射击事件、实体状态来自不同记录通道，关联时需保留原始 tick、sub-tick offset（若可用）、SteamID、实体句柄及来源字段。

## 2. Demo 是服务器记录，不等于玩家屏幕录像

Valve 在 2025-11-04 发布 TrueView：它通过重新运行被观察玩家的客户端预测，使 demo 回放更贴近该玩家当时的体验。Valve 同时说明，TrueView 需要相符的客户端版本（否则默认关闭），旧 demo 可能不兼容，而且即使启用，慢放时仍会有显示时序差异。

因此，纯 Python / Rust 的静态 demo 表格解析不能声称还原了“玩家当时屏幕上看到的每一帧”。精确的客户端预测画面属于 CS2 客户端重放能力；字段级解析可以提供服务器事件、状态和可见性提示，不能自动替代 TrueView。

## 3. 事件与实体状态是两条数据通道

- **事件**记录离散事实，例如 `weapon_fire`、`player_death`、`player_hurt` 和 `flashbang_detonate`。
- **实体 / 比赛规则状态**记录某个 tick 上的属性，例如位置、血量、阵营、装备、`flash_duration` 和回合胜负状态。

建议的分析模式是“事件定位、状态解释、交叉校验”。比如用死亡事件定位死亡时刻，再查前一个 tick 的 inventory；用闪光爆炸事件定位，再查玩家闪光状态变化；用回合胜负状态转变切分回合，再与可用的回合事件核对。

事件是否存在、字段类型和更新方式可能因录制来源、demo 版本和解析器版本变化。解析层必须对必需字段做显式存在性、非空率和取值范围检查；缺字段不能静默地变成 0、False 或“无问题”。

## 4. 可达到的分析精度分层

### A. 可做成精确、可复核的结果

- demo 中实际记录的事件、事件 tick、事件关联的 SteamID；
- demo 中实际保存的实体状态值及其 tick；
- 在身份和回合关联正确前提下，对事件计数、伤害、装备、经济、回合结果做确定性汇总；
- 以 demo 自带字段为证据的时间线与游戏内跳转位置。

“精确”指忠实于解析出的 demo 数据，不等于这些数据描述了完整的玩家主观体验。

### B. 依赖假设的派生指标

- **开火速度 / 急停**：由相邻状态样本差分；本质是区间平均速度。sub-tick 输入时间无法补回未记录的连续位置。
- **反应时间**：`spotted` 是雷达发现状态，不等于真实视线建立。项目样本显示其更新过疏，不适合估计 0.2–0.3 秒量级的反应时间。
- **准星到目标角度**：视角和坐标可读，但若没有对应的骨骼 / hitbox 快照，就只能按站立、蹲姿等高度模型估算身体目标点。
- **压枪 / 子弹落点**：可分析已记录的射击角度、后坐力、精度和命中事件；未命中子弹原本瞄准谁，以及墙体、烟雾和目标可见性，不能只靠这些字段确定。
- **购买时刻**：某些录制源缺少购买结束事件，只能按冻结结束时间和 `mp_buytime` 推算。

所有这类指标应携带 `method`、`assumptions`、`confidence`、`sample_count` 和原始证据引用；低样本或前提不成立时应输出“证据不足”，不应给确定性训练结论。

### C. 单靠现有字段不能可靠还原的事实

- 玩家显示器上精确呈现的每帧画面与反应时刻；
- 未知目标的真实可见性、遮挡、烟雾透视关系；
- 未记录的 sub-tick 连续位置 / 鼠标轨迹；
- 缺少 hitbox / 骨骼快照时每发未命中子弹的意图目标；
- demo 未记录或 parser 未解码的数据。

这些项目需要 CS2 客户端的版本匹配重放（如 TrueView）、相应 demo 数据、地图几何 / 可见性计算，或其他可信数据源。算法优化不能凭空补回未记录的信息。

## 5. 建议的引擎感知数据流水线

1. **识别来源与版本**：保存 demo header、游戏 patch、地图、录制来源、demo tick rate、parser 版本 / 提交。
2. **批量解析并标准化**：把事件附近需要的 tick 和属性合并成一个稀疏查询，并用一次全时间轴比赛规则查询切分回合。当前 demoparser Python API 仍需要按事件名分别查询；想做到整个 demo 真正单次顺序扫描，需要底层流式解析器支持。
3. **做完整性门禁**：验证目标玩家身份、关键属性覆盖率、连续 tick 缺口、阵营变化、warmup、回合数和事件关联率。门禁失败则拒绝相关检测项。
4. **保留原始与派生层**：原始 parser 值不可覆盖；派生值保存公式、所用 tick、单位和假设，确保复算与审计。
5. **以事件为中心计算**：围绕击杀、死亡、伤害、投掷物和回合边界，批量取相关窗口；不需要所有玩家所有 tick 的所有属性。
6. **结论附证据**：每条诊断引用真实的回合、tick、事件和字段；UI 可提供 CS2 内跳转。对视觉判断优先链接匹配版本的 TrueView 回放，而不是把 server-side 位置描述成“玩家看见了”。
7. **按 demo 来源建立回归矩阵**：Valve、赛事、完美、5E、FACEIT；不同 patch、demo 版本、64/128 tick 标签、加时、热身、分卷压缩包。新引擎更新先检查 schema 和已知字段，再开放相应规则。

## 6. 本仓库当前上限

本项目现有 CLI 可生成 JSON/Markdown 报告，涵盖击杀/阵亡/助攻、伤害、补枪窗口、闪光状态、移动开火样本和购买窗口经济快照；事件 tick、SteamID、阈值、字段缺失和精度限制会随报告保留。AI 主观诊断、地图几何视线判断、职业基准对比和本地网页尚未接入。

当前实现通过批量 tick 查询控制重复扫描，但 demoparser 的事件接口仍按事件分别调用。最大可见性能改进需要引入支持增量输出事件与网络属性的单遍解析接口；在没有该接口前，直接循环调用 `parse_ticks` 会重复扫描整份 demo，不能靠 Python 小优化消除这部分 I/O / 解码成本。

即使后续完成流水线，合理的产品上限也应分两种：

- **数据诊断上限**：对 demo 实际记录的服务器事件 / tick 状态给出精确、带证据的统计与模式分析；
- **观战教练上限**：依托匹配版本的 CS2 客户端 TrueView 及地图 / hitbox / 可见性数据，尽量重建玩家体验。它仍不是绝对逐帧还原，Valve 明确说明回放与原始体验可能存在差异。

所以项目可以做到“数据证据充分的复盘助手”，但若只使用当前的静态字段解析，不能承诺完全替代主播逐帧看 POV demo。
