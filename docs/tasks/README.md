# 任务单

Claude 写任务单，实现方（Codex 或 Kimi，按难度分配）按任务单实现，Claude 审查。协作规则见仓库根目录的 `AGENTS.md`。

## 流程

1. Claude 和用户确定方案后，按类型在对应目录新建任务单（从 `TEMPLATE.md` 复制，编号规则见下方"三类任务"），状态为"待做"。
2. 用户在 Codex 中指定任务单，例如："按 docs/tasks/fixes/026-xxx.md 实现"。
3. GPT 实现，跑通测试，填写"完成报告"，状态改为"待审查"。
4. Claude 审查工作区的改动（`git diff`），并实际运行测试或 demo 验证：
   - 通过：状态改为"完成"，用户确认后提交；
   - 不通过：在"审查意见"中逐条写明问题，状态改为"需修改"，回到第 3 步。

## AI 分工（2026-10-17 确定）

| 角色 | 由谁做 | 做什么 |
|---|---|---|
| 主控（只有一个） | Mac 上的 Claude | 和产品负责人沟通、定方案、写任务单、审查、合并、推送；审计判定；手工算样例 |
| 主力实现 | Codex | A 类任务，以及 Kimi 不可用时的 B 类任务 |
| 第二实现 | Kimi Code | B 类任务。头 2–3 个任务 Claude 逐行审查，合格后按常规审查 |
| Windows 助手 | Windows 上的 Claude | 只做需要 Windows 的事：游戏内复盘、CS2 命令验证、本地模型和小模型实验；不写任务单、不合并 |

- **判定不外包**：审计判定和"程序判对没有"的结论只由 Claude 和产品负责人定，实现方不参与。
- **产品里的 AI**（DeepSeek、本地模型）只用于生成报告，不参与开发。

## 难度分级

每份任务单写明难度，按难度分配实现方：

| 难度 | 判断标准 | 执行 | 例子 |
|---|---|---|---|
| **A 难** | 新算法、跨多个模块，或者写不出确定的预期结果 | Codex，思考强度 high | 检测算法改口径、白名单检查器、视野几何、解析层 |
| **B 中** | 照着现有写法扩展，改 1–3 个文件，Claude 能事先写出测试 | Kimi；Kimi 不可用时 Codex，思考强度 medium | 新增排除条件或检测规则、新增配置项、报告排版、审计脚本小功能 |
| **C 小** | 改动少于约 50 行，或写任务单比直接改还费事 | Claude 直接实现，任务单注明 | 改阈值、改文案、单点修 bug |

- **Kimi 不做**：解析层、视野几何、检查器的整体结构。这些地方一错所有结论跟着错，审查也最难发现。
- **Kimi 没有沙箱**：只在任务分支的独立工作目录（`git worktree`）中运行，不在主工作目录运行。
- **交给 Kimi 的 B 类任务先写测试**：Claude 在任务单"预写测试"中给出测试文件，实现方只负责让它们通过，不得修改。交给 Codex 的 B 类任务可以只在验收标准里列出用例。

## 节省额度的约定

返工、通读文档和重复跑测试是最大的浪费：

1. **减少返工**：任务单写明预期输出的具体数字；B 类先写测试；实现方遇到不确定就停下提问，不要猜着做完。
2. **背景最小化**：任务单只列函数名、配置段和章节，不让实现方通读大文档（`docs/features.md` 约 35KB）。
3. **测试分两步**：开发时只跑相关测试文件，完成前跑一次全部测试；报告只贴最后一行。真实 demo 验证由任务单指定一场、一条命令、要看哪几行。
4. **小改动攒一单**：每份任务单都有读背景、跑测试、写报告、审查的固定开销，零散小修改合并成一份。
5. **按清单审查**：Claude 先看改动文件列表、跑测试，再细看任务单列出的关键点。
6. **Claude 会话**：一个大阶段一个会话，进度写进 `docs/status.md`，新会话从那里接着做；验证过的数据结论写进 `docs/fields.md`，不重复验证。
7. **Codex 思考强度**：全局默认 medium（`~/.codex/config.toml`），A 类任务启动时加 `-c model_reasoning_effort="high"`。
8. **并行默认**：重建基准、跑回归时默认 6 进程并行（`tools.jobs`），用 `--jobs 1` 退回串行。

## 状态

`待做` → `待审查` → `需修改` ↔ `待审查` → `完成`

## 写任务单的要求（给 Claude）

- **交出任务单之前，先跑一遍预写测试**（S06，2026-10-17）：逐条确认失败的原因都是"功能还没实现"，而不是测试本身的预期值、数据边界或字段名写错了。还要找出会因新功能失效的旧测试，比如写死的问题总数，一并列进允许修改的清单。
- **验收标准要可检查**：写明具体的测试用例、命令和预期输出，不写"实现得好"这类无法检查的要求。
- **写清接口**：函数签名、数据结构、配置键名、输出格式。
- **写清范围外**：明确哪些不要做，防止顺手改动。
- **背景只列必须读的**：具体到文件和章节，不让 GPT 通读整个仓库。
- 涉及 demoparser2 字段和数据口径的结论，要写明已经验证过的事实和出处，不让 GPT 凭记忆猜。
- **有面向玩家的输出时，必须填模板里的"玩家看到什么"**（2026-10-18，043/044 的教训）。

## 审查面向玩家的输出（给 Claude）

只核对数字算得对不对是不够的（2026-10-18：准星同时出现在优点和问题里、单位看不懂、结论选了只出现 7 次的问题，都是产品负责人看页面时才发现）。审查时：

1. 用**至少 3 名水平不同的玩家**的真实数据生成页面，例如产品负责人本人、另一名业余玩家、一名职业选手；
2. 站在玩家的角度逐块读：看不看得懂、区块之间有没有矛盾、说法有没有超出数据能支持的范围；
3. 跑 `scripts/page_check_all.py`（045 起），违规必须为 0 或逐条说明原因；
4. 说明文字要对照指标的实际计算代码核对，不能只看指标名。

## 三类任务

按类型放在三个目录里，分开管理：

| 目录 | 类型 | 针对什么 | 验收 | 编号 |
|---|---|---|---|---|
| `features/` | 功能 | 新增产品能力：新命令、新报告内容、新数据 | 指定的用例通过，真实 demo 上输出符合预期 | 三位数，和 `fixes/` 共用一个递增序列 |
| `fixes/` | 修 bug | 实测、评测或审查中发现的具体问题：规则漏洞、误判、口径错误、实现缺陷 | 复现问题的用例改后通过，原有用例不受影响 | 三位数，和 `features/` 共用一个递增序列 |
| `structural/` | 结构性改进 | 一整类问题反复出现的原因 | **先量出改动前的指标，再量改动后的**，用数字说明这一类问题少了多少；同时留下一个以后能反复运行的测量工具 | `S` 加两位数（019–021 是建立这条线之前做的，保留原编号） |

- **功能和修 bug 共用一个序列**（下一个是 051），这样"任务 0NN"在整个项目里始终唯一，代码注释和文档里的引用不会混淆。
- 一份任务单只放一类。如果一个功能做到一半发现 bug，另开一份 `fixes/` 任务单，不要混在功能任务单里。
- 不确定该放哪类时，看它的起因：**起因是"现在不对"的**放 `fixes/`；**起因是"还没有"的**放 `features/`；**起因是"同一类错反复出现"的**放 `structural/`。

## 结构性改进的方向

2026-10-17 回顾时发现，修 bug 任务里的问题大致分四类，对应四个结构性方向：

| 问题类型 | 例子 | 结构性方向 | 任务 |
|---|---|---|---|
| 程序检测误判 | R4 看见对手前的 11 发子弹被算成"压枪差" | 测量每条检测规则的准确率，并对全部 demo 做可疑组合扫描 | S01 |
| 口径和外部平台不同 | 补枪 3 秒对 5 秒、道具伤害用原始伤害 | 把平台数据固定成回归对照，口径一偏差就报错 | S02 |
| AI 说法写错 | "近距离 AK 对拼"、"慢主要在看见到开枪" | 检查器从黑名单改成白名单：事实性描述词只能来自程序占位符 | S03（任务单已写，见索引） |
| 产品逻辑没想清楚 | 高光选了最慢的那次、▲▼ 并列全都标 | 流程约定（不需要单独写任务单）：凡是"程序替用户做选择"的功能，Claude 先用 5 场真实比赛手工走一遍、给产品负责人看过样例，再写任务单 | — |
