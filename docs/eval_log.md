# 评测记录

改提示词、检查器、占位符规则或换模型之后，用固定的评测集重新生成报告，人工核对错误数，记在这里。目的是用数据判断改动有没有让报告变好，不再靠零散的个例（任务 021）。

## 怎么做

仓库内的玩家名已匿名，与本地评测清单的 case 名不一致是预期的。

1. 评测清单在 `data/eval/eval_set.toml`（含真实 steamid，不入库；格式见 `config/eval_set.example.toml`）。
2. 运行：`python scripts/eval_batch.py --label <这次改了什么> [--provider ...] [--model ...] [--only 关键词] [--jobs 5]`。真实调用会产生费用，脚本会先确认；用 flash 跑一整套大约 0.3 元。API 模型默认 5 个 case 并行，本地模型固定 1 个；每个 case 的输出在它目录下的 `run.log`。
   - 只改了检查规则时不用重新生成：`python scripts/eval_recheck.py <评测目录>` 用新规则重查已保存的提交，不花钱。
   - 多场汇总的逐场分析结果缓存在 `data/cache/analysis/`，代码、配置或 demo 不变时第二次直接读取（汇总从约 4 分钟降到约 7 秒）。
3. 输出在 `data/output/评测/<日期时间>_<label>/`，每个 case 一个文件夹，汇总表是其中的 `summary.md`。
4. Claude 逐份核对报告：对照 `moments.json`、`facts.md`、`problems.md`，把错误直接用"⚠️ 核对"标在报告里，把错误数填进 `summary.md` 最后一列。
5. 在下面新增一节。

## 错误怎么算

| 类型 | 算不算错误 | 例子 |
|---|---|---|
| 事实错误 | 算 | 把击杀写成死亡；说"已下包"但实际没下包；数字含义写错 |
| 编造细节 | 算 | "瞄准腰部而不是头部"，数据里没有瞄准部位的信息 |
| 没有依据的概括 | 算 | "占比最高"，数据里没有统计这一项 |
| 例子选得不当 | 算 | 用勉强过线的交火当代表 |
| 轻微夸大 | 单独记，不计入错误数 | 48 血说成"残血" |
| 写得空泛 | 不计入，在备注里写 | "多练习" |


- **结论**：分级让本地模型从"大多失败"变成"稳定出报告"，L0 部分保证正确。但 L1 的文字仍有错误、也不好读，不能直接当作付费内容。
- **可以继续试的方向**：
  - L1 改成更窄的任务，例如只填"一句话说明"的模板，并禁止"导致"这类因果词；
  - 把 L1 交给 flash，成本很低，预计错误接近 0；
  - 免费档只给 L0。

## 2026-10-17 检测规则审计（S01 第一批判定）

- **做法**：
  - 用 `scripts/audit_collect.py` 跑完 24 场业余 demo、240 人次，包括停用的规则，共 6669 条命中；

- **判定口径**：程序说"这次交火有这个问题"，教练会不会同意。correct 表示事实成立且值得提醒；wrong 表示事实不成立或不是这个问题；unsure 表示光看数据判断不了，不计入准确率。
- **结果**（整体为加权准确率；括号内为启用状态）：

  | 准确率 | 问题 |
  |---|---|
  | ≥ 90% | 下包后带着火没用 100%、沙鹰移动开枪 100%、及时补枪 100%、闪光助攻 100%、被闪中后被击杀（停用）100%、Glock 远距离 95%、出枪慢 92%、没看见就被打死（停用）90%（待游戏内确认）、有道具直接拉出 90% |
  | 75–90% | 人数优势冒进 85%、拉出撞架点 79%、扫射时移动（停用）78%、先发现先开枪 78% |
  | < 65% | 准星没提前放好 62%（另有 9/20 判不了）、漏补枪 60%、压枪差 55%、开枪时没停稳 47%、武器还不能开枪（停用）20% |

- **错误原因**（wrong 89 条、unsure 26 条）：

  | 原因 | wrong | unsure | 影响的规则 |
  |---|---:|---:|---|
  | 穿烟：几何视野不算烟 | 33 | 3 | 出枪慢、准星、压枪、先发现先开枪、拉出类 |
  | 非可避免（正常开枪间隔内被击杀） | 16 | 0 | 武器还不能开枪 |
  | 看见前已开枪：判的是预瞄或乱扫的子弹 | 9 | 5 | 开枪时没停稳、出枪慢、准星 |
  | 交火中被闪白 | 8 | 2 | 压枪、开枪时没停稳、准星、拉出类 |
  | 贴阈值 | 8 | 4 | 开枪时没停稳（速度比 0.34–0.36）、准星、Glock |
  | 已被其他队友补上 | 6 | 0 | 漏补枪；全部命中中占 207/683（30%） |
  | 事实不符（穿墙击杀、被燃烧瓶烧死） | 5 | 0 | 拉出类、没看见就被打死 |
  | 对手正被你闪白时拉出 | 2 | 0 | 拉出撞架点 |
  | 噪声领先（领先 1–2 tick） | 2 | 0 | 先发现先开枪 |
  | 跟枪成分：分不清预瞄差还是在跟移动目标 | 0 | 7 | 准星没提前放好 |
  | 视野可疑：漏补只看直线距离 | 0 | 5 | 漏补枪 |

- **结论**：
  1. 绝大多数错误不是规则写错，而是**少了排除条件**：穿烟、穿墙、交火中被闪、看见前已在开枪、已被队友补上。这几个条件数据里都有，可以统一加一层排除。
  2. "开枪时没停稳"应该判**看见对手之后**的第一枪；"先发现先开枪"要求领先至少 3 tick。
  3. "准星没提前放好"在单次交火上有一半分不清是预瞄差还是跟枪，需要另算"第一次看见时准星与对手的夹角"，这才是纯预瞄。
  4. 漏补枪要排除"已被其他队友补上"的情况，并补上"这段时间能否看到击杀者"的视线判断。
  5. "武器还不能开枪"继续停用，或者改成"栓狙空枪后 0.5 秒以上仍未处理"。
- **待办**：
  - 8 条需要产品负责人进游戏确认（没看见就被打死 3 条、准星跟枪 2 条、看见前 1 发 1 条、漏补枪 2 条）；
  - 统计脚本的已知问题：某一层准确率为 0% 或 100% 时，分层方差为 0，置信区间退化成一个点（例如出枪慢显示 91.9%–91.9%），需要改用更稳的区间估计。
